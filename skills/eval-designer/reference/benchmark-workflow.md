# Benchmark Run Structure

This is the directory shape both `axiomatic-spec-workspace` and `grounded-research-workspace` converged
on independently. Use it as-is; it's also exactly what skill-creator's aggregation script and viewer
expect.

## Directory shape

```
<workspace>/
├── evals/evals.json                       # canonical list of eval cases (see eval-case-design.md)
├── fixtures/<name>/                       # real small repos/data the prompts reference
├── trigger-evals/                         # skill/description trigger accuracy — separate axis, separate dir
│   ├── trigger_eval_set.json
│   ├── candidate_description_v1.txt
│   ├── candidate_v1_results.json
│   └── run_eval_candidate_v1.log
└── iteration-<N>/
    ├── run_map.json                       # {run_hash: "eval-name/with_skill|without_skill"} for the viewer
    ├── benchmark.json                     # aggregated stats, see schema below
    ├── benchmark.md                       # human-readable version of the same
    ├── review.html                        # generated by generate_review.py, opened for human review
    └── eval-<name>/
        ├── eval_metadata.json             # {eval_id, eval_name, prompt, assertions}
        ├── with_skill/run-1/
        │   ├── outputs/                   # everything the candidate produced, incl. transcript.md
        │   ├── grading.json               # per-expectation pass/fail + evidence (agents/grader.md schema)
        │   └── timing.json                # {total_tokens, duration_ms, total_duration_seconds}
        └── without_skill/run-1/
            └── ... same shape
```

`with_skill` / `without_skill` are the literal configuration labels the viewer groups by — keep using them
even when evaluating a non-skill product feature. In that case, put one line at the top of `benchmark.md`
clarifying what each label means for this run (e.g. "with_skill = candidate prompt v3, without_skill =
current production prompt").

> **Program example (Gauntlet AI, "Evaluations Part 1" deck, `slides.pdf` + `prod-evals-cookbook`, shared
> 2026-09-16 by Byron Mackay, #cohort-main).** For the `fixtures/<name>/` directory above, the deck's
> "Replay Harnesses" stage names a specific record/replay split this file doesn't otherwise spell out:
> capture one real agent session (a live call, tool results included) once to a JSON fixture
> (`record_session(query=..., session_id=...)` → `fixtures/<id>.json`), then `replay_session(id)` +
> `evaluate_session(...)` against that frozen snapshot as many times as needed — immediately, next week, or
> after a human has annotated ground truth onto it — at zero further LLM cost. The deck's tagline: "record
> once, score anytime." This decouples the expensive part (a live run) from the cheap part (re-grading),
> which matters once `iteration-<N>/` starts accumulating many re-grades of the same underlying trace.

## Running it

1. Locate skill-creator's scripts once:
   ```bash
   SKC_DIR=$(find ~/.claude -type d -name skill-creator -path '*skills/skill-creator' 2>/dev/null | head -1)
   ```
2. For each eval case, spawn two subagents in the *same* turn (candidate + baseline) — never spawn one
   batch and come back for the other later, or wall-clock/tokens won't be comparable. Each subagent gets:
   the skill path (or feature-under-test spec) if it's the candidate, the eval prompt, any input files, and
   an explicit output directory to write to plus what to save (transcript, output files, `metrics.json` if
   you want tool-call counts).
3. As each subagent's completion notification arrives, immediately write its `timing.json`
   (`total_tokens`, `duration_ms`, `total_duration_seconds`) — this data does not exist anywhere else after
   the fact.
4. Grade each run (skill evals: reuse `agents/grader.md` from skill-creator verbatim, spawned as a
   subagent or done inline; feature evals: see `reference/llm-judged-rubrics.md` for the rubric variant of
   the same protocol). Write `grading.json` next to `outputs/` in each run directory.
5. Aggregate:
   ```bash
   cd "$SKC_DIR" && python3 -m scripts.aggregate_benchmark \
     <workspace>/iteration-<N> --skill-name <name>
   ```
   This produces `benchmark.json` and `benchmark.md` with mean/stddev/min/max for pass_rate, time_seconds,
   and tokens per configuration, plus a delta. Do not hand-write these unless the script genuinely can't
   apply (e.g. custom non-`with_skill`/`without_skill` labels) — if you do, match the schema in
   skill-creator's `references/schemas.md` exactly; the viewer reads field names literally
   (`configuration`, not `config`; `result.pass_rate`, not a top-level `pass_rate`).
6. Do an analyst pass over `benchmark.json` before showing it to anyone: which expectations are
   non-discriminating (pass in both configurations), which evals show high spread, whether token/time cost
   is worth the pass-rate gain. `agents/analyzer.md`'s "Analyzing Benchmark Results" section in
   skill-creator is the right prompt for this if you spawn it as a subagent.
7. Launch the viewer for human review:
   ```bash
   nohup python3 "$SKC_DIR/eval-viewer/generate_review.py" \
     <workspace>/iteration-<N> --skill-name "<name>" \
     --benchmark <workspace>/iteration-<N>/benchmark.json \
     > /dev/null 2>&1 &
   ```
   Pass `--previous-workspace <workspace>/iteration-<N-1>` from iteration 2 onward. In a headless
   environment, use `--static <path>` instead of starting a server.

## Iterating

A new iteration is a new `iteration-N+1/` directory, not an overwrite — keep the old one so
`--previous-workspace` comparisons and the historical benchmark deltas both still work. Only rerun the
eval cases that changed or that are still relevant; note in `benchmark.md` which cases carried over
unchanged from the prior iteration versus which are new.

## What "candidate" means when there's no skill

For a product feature (no `SKILL.md`), "with_skill" = the treatment being evaluated (new prompt, new
model, new post-processing rule) and "without_skill" = whatever it's being compared against — current
production behavior, a naive baseline, or a previous candidate mid-iteration. The subagent's task
description changes accordingly (e.g. "call the co-pilot's suggestion endpoint with this patient
context using prompt version 3" instead of "use the skill at this path"), but every other mechanic —
timing capture, grading against expectations, aggregation, the viewer — is unchanged.
