# Software Factory & Unity: Architecture, Transfer Context, and Implementation Roadmap

This document serves as the primary handover and architectural synchronization point between the **Software Factory** orchestrator and its core semantic dependency, **Project Unity**.

## 1. System Architecture & Inter-Repository Context

The two repositories operate as complementary layers in an autonomous software engineering pipeline:

```
+-------------------------------------------------------------------------+
|                            SOFTWARE FACTORY                             |
|  Orchestrator, Governance, & Verification Pipeline                      |
|                                                                         |
|  [Spec/Issue] ──► [One-Way Door Guard] ──► [Socratic ADR Generation]   |
|                          │                                              |
|                          ▼                                              |
|  [Deterministic QA Gate] ◄── [Synthesis Agent]                          |
+──────────────────────────┼──────────────────────────────────────────────+
                           │ Queries & Ingests Context
                           ▼
+-------------------------------------------------------------------------+
|                                UNITY                                    |
|  Universal Semantic Intermediate Representation Engine                 |
|                                                                         |
|  Source Code (Py/Go/Rust) ──► Tree-sitter AST ──► Normalized UAST       |
|                                                          │              |
|                                                          ▼              |
|  Context Ingestion ◄── Canonical Unity-IR ◄── Invariant & Contract Pass |
|  (Invariants, ΔS)       (3-Layer Schema)                                |
+-------------------------------------------------------------------------+
```

### Repository Roles
1. **`software-factory`:** 
   The execution engine and director. It handles project intake, audits architectural risk (One-Way vs. Two-Way doors), records formal Architecture Decision Records (ADRs), guides code synthesis, and runs deterministic verification gates.
2. **`unity`:** 
   The semantic context engine. It deterministically compiles heterogeneous multi-file codebases into a canonical, language-agnostic intermediate representation (**Unity-IR**). This representation normalizes language syntax, eliminates cross-lingual bias (e.g., Python vs. Go/Rust), preserves systems-level invariants (concurrency locks, memory ownership, side-effect purity), and eliminates the multi-second retrieval latency of external Graph RAG databases.

## 2. Core Architectural Philosophy: Parity Over Panopticon Telemetry

A foundational thesis guiding both repositories is the rejection of the **"Panopticon Telemetry"** pattern prevalent in contemporary agentic engineering:
- **The Failure of Extrinsic Surveillance:** Current workflows attempt to constrain stochastic LLM code generation by wrapping models in extensive synthetic test generators, runtime eBPF sandboxes, and multi-tier review guardrails. This causes **tautological test debt** (LLMs writing brittle tests for code generated by LLMs) and severe **human review fatigue**.
- **The Unity Invariant Model:** Unity establishes **intrinsic semantic parity**. By deterministically lowering code into formal preconditions ($\mathcal{P}$), postconditions ($\mathcal{Q}$), ownership bounds, and state transition equations, correctness becomes an algebraic property of the representation. Reviewers and agents audit the **canonical semantic delta**:
  $$\Delta \mathcal{S} = \mathcal{S}_{	ext{post}} \ominus \mathcal{S}_{	ext{pre}}$$
  $$\Delta \mathcal{S} = \mathcal{S}_{\text{post}} \ominus \mathcal{S}_{\text{pre}}$$
  rather than parsing hundreds of lines of syntax boilerplate.

## 4. Key Architectural Decisions (Ratified)

1. **Bare-Metal Orchestration:** `software-factory` will use a lightweight, async Python CLI runner communicating directly via official model SDKs (Gemini SDK / Anthropic SDK / OpenAI SDK) rather than bloated third-party agent frameworks.
2. **Dual-Anchor Language Proof:** For the initial implementation of `unity`, focus strictly on **Python + Go**:
   - *Python:* Dynamic, duck-typed, ubiquitous.
   - *Go:* Statically typed, explicit error handling, native CSP concurrency (mutexes, goroutines, channels).
   - Demonstrating that both implementations lower to an identical, canonical `Unity-IR` representation directly proves cross-lingual parity.
3. **Deterministic Lowering Pipeline:** Translation to `Unity-IR` must be performed by static analysis passes (Tree-sitter $	o$ CFG/DFG $	o$ Invariant extraction $	o$ Canonical Emitter). At no point should an LLM be used to generate `Unity-IR` from source code, preventing probabilistic translation error.

## 5. Phased Implementation Roadmap

### Phase 1: Engine Foundations & Core Scaffolding

#### Track A: `unity` (Compiler Frontend)
1. Scaffold package structure under `compiler/`:
   ```
   compiler/
   ├── __init__.py
   ├── parser.py          # Tree-sitter multi-language parser wrapper
   ├── uast.py            # Normalized Universal AST data structures
   ├── extractor.py       # Static invariant & contract extractor
   └── emitter.py         # Unity-IR 3-layer text serializer
   ```
2. Configure Tree-sitter parsers for Python (`tree_sitter_python`) and Go (`tree_sitter_go`).
3. Implement the AST walker to extract:
   - Function signatures, parameter types, return signatures.
   - Concurrency bounds: mutex lock/unlock calls, channel operations.
   - State mutations: assignment to shared/reference structures.
4. Implement `emitter.py` to format extracted data into valid 3-Layer Unity-IR:
   - Layer 1: Contract & System Semantics (`CONTRACT`, `SYSTEMS`).
   - Layer 2: Algorithmic Logic & Predicates (`PRECONDITIONS`, `EXECUTION_LOGIC`, `POSTCONDITIONS`).
   - Layer 3: Causal Intent & Symbol Links.

#### Track B: `software-factory` (CLI Runner & Governance)
1. Scaffold the core CLI entrypoint (`cli.py` / `factory.py`):
   - Command: `factory run --spec <path_to_spec.md> --repo <target_repo_path>`
   - Command: `factory audit --pr <diff_or_commit>`
2. Implement **Stage 1: One-Way Door Guard**:
   - Inspects the spec/diff against risk categories (storage schemas, security/auth boundaries, public API contracts, vector dimensions).
   - Flags changes as Two-Way Doors (proceed autonomously) or One-Way Doors (trigger mandatory ADR generation).
3. Implement **Stage 2: Socratic ADR Generator**:
   - When a One-Way Door is flagged, automatically synthesizes a formal ADR using `templates/adr-template.md`.

---

### Phase 2: Integration Bridge & Deterministic QA

#### Track A: `unity` (Semantic Delta & Parity Verification)
1. Implement the Semantic Delta Engine ($\Delta \mathcal{S}$):
   - Given a git diff or two ASTs, emit only modified preconditions, mutated invariants, and altered contract signatures.
2. Build parity test cases:
   - Implement an identical concurrent financial ledger in both Python (with `threading.Lock`) and Go (with `sync.Mutex`).
   - Run both through `unity` and verify that the emitted `Unity-IR` is structurally identical.

#### Track B: `software-factory` (Unity Context Ingestion & QA Gate)
1. Integrate `unity` into the factory pipeline:
   - When the factory ingests repository context for synthesis, it invokes `unity` to lower relevant files into high-density `Unity-IR` rather than feeding raw source code.
2. Implement **Stage 3: Deterministic QA Gate**:
   - Runs syntax validation, targeted unit test suites, and the `comprehension-debt-and-interface-auditor` pass to prune excessive public surface area before creating commits.

### Phase 3: Brownfield Demonstration & Comparative Benchmarking

1. **End-to-End Brownfield Trial:**
   - Execute the factory against a realistic multi-file codebase containing an intentional cross-file concurrency or state-synchronization defect.
   - Verify that the factory:
     1. Ingests the issue description.
     2. Lowers the multi-file context into `Unity-IR`.
     3. Locates and resolves the cross-file invariant violation.
     4. Passes the deterministic QA gate and produces a clean patch.
2. **Benchmark Generation:**
   - Run a comparative measurement across three context mechanisms:
     - *Baseline 1:* Raw source code.
     - *Baseline 2:* Simulated Graph RAG.
     - *Condition 3:* Unity-IR.
   - Record and output metrics:
     - **Retrieval & Parsing Latency:** Target $<100	ext{ms}$ (Unity) vs. $2	ext{--}8	ext{s}$ (Graph RAG).
     - **Token Density:** Target $\ge 40\%$ reduction in token volume.
     - **Resolution Correctness:** Execution accuracy of generated patches.
3. **Artifact Packaging:**
   - Generate automated execution logs, terminal recording artifacts, and clean documentation for both repositories.
